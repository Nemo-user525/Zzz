### 1. 按价值排序交付，先保证主 Demo

**P0：真实 API + 可追溯证据 + 即时重算 + 稳定离线演示。** 启动后不用搜索即可进入预置企业；首次看到公司身份、覆盖范围、资料日期、一个可点开的风险事件、带报告期与来源的财务事实，以及「尚未核实」项。点击「推演这笔订单」，用明确标记为**情景假设**的延付 30 天计算；拖预付款 0%→30% 时，调用后端重算并清楚显示最低现金从 3 万元变成 33 万元，20 万元底线由「缺口 17 万元」变为「未跌破」。点击「这怎么算的」显示公式与资金发生日；打开核对卡能区分公开事实、情景假设、计算结果。

**P1：把可演示的页面变成可信、顺手的产品。** 页面适配 1920×1080 大屏和普通笔记本；重要操作始终易找，字体与对比度足够，信息不会被滚动或抽屉遮挡。处理加载、空结果、无网、接口失败、重试、快速连续拖动、无效输入、重置演示。视觉效果服务于理解，不能用颜色、动画或虚构「风险分」冒充结论。

**P2：扩展性与稳健性。** 导入与查询应能接受以后增加已核验企业和用户场景的配置，不依赖唯一企业 ID 或角色文案；做必要的数据库约束与测试。不要为了架构美观重写现有数据模型、证据服务或现金引擎。剩余时间优先修主流程瑕疵，其次再考虑同业对照或锦上添花。

初赛四个维度各占 25%，你负责把它们变成评委当场可见的证据：**主题完成度**看真实企业身份、风险事件、财务事实及可点来源；**商业价值**看「供应商签约前如何决定预付款和账期」是否一眼明白，并把收费想法标为待验证假设；**创新性**看同一笔订单怎样把公开线索、未知项和可调现金情景连起来，强调这是用户主动测试压力，不是预测客户会延付；**技术质量**看幂等导入、来源核验、契约一致、后端确定性计算、离线可用和实测记录。页面不要堆叠没有证据的指标来迎合评分。

### 2. 数据库与导入：在现有模型上增强

1. 保持 `companies`、`sources`、`facts`、`risk_events`、`demo_scenarios`、`import_logs` 的用途和主键稳定。真实企业事实、官方来源、风险事件与虚构交易情景分离；用户角色、决策目标、输出模板仍由 `data/use_cases.json` 配置，不写入企业事实表。若现有约束不足，以最小兼容改动加唯一性、外键、非空或索引，并说明对现有 SQLite 文件的处理方式；不能删除用户已有数据库来掩盖迁移问题。
2. `seed` 可重复执行，连续运行两次不增加公司、来源、事实、事件的数量，也不因同一公告转载增加事件数。允许导入未来增加的 `data/verified/*.json`，而非永远只认一个硬编码文件；但新增数据必须来自主负责人维护的核验文件，不由你或模型编造。先核对清单与结构化数据的 source ID、company ID、页码、报告期、单位和缺失字段；重复 ID、重复 URL/SHA-256、悬空引用、非法金额或不一致的事件主体需给出可定位的错误或降级状态。当前的 1/2/4/1 数据导入后仍可用。
3. 每个公开事实应能回到来源 ID、官方 URL、页码、原文短摘录、SHA-256、发布时间/采集时间；导入核对文件哈希和摘录定位。对中文无法直接抽取的 PDF，沿用已记录的人工复核范围，不能把「只核验到数字字符」表述为自动核实整段中文。缺失、冲突、哈希不符或未人工复核的数据不得被前端标记为「已核验」。金额统一以 API 的人民币**元**为单位，前端才换算为万元；保留财报期、合并/母公司口径和审计状态。
4. 对旧状态、坏输入和半途失败做一次真实验证：导入失败不留下「半份官方公告已核实」的混合状态；成功导入可在 `/api/health`、企业详情、风险事件与来源接口看到一致数量。导入日志写实际结果，不把重复运行的日志条数当作新增来源。若要改变 API 或核心证据规则，写问题和最小修改建议交给主负责人处理。

### 3. 前端与 API 客户端：让展示与事实完全一致

1. 严格对照 `docs/openapi.yaml` 检查 `frontend/src/api/types.ts`、`client.ts`、`mock.ts`。首页正常模式调用真实 `/api`，Vite 代理到 `http://127.0.0.1:8000`；`mock` 仅供独立开发或演练，必须与真实响应的字段、类型、单位、空值一致，并显眼标明 mock 模式。不能在 API 出错时无提示地切成示例结果。统一处理结构化 `code/message/details` 错误和网络错误，给用户可执行的重试或启动提示。
2. 首页证据卡按 API 实际数据渲染。每个风险事件显示发生/披露时间的准确口径、事件主体、阶段、核验状态、状态更新及对应来源；不把 Zinitix 事件归到母公司身上。每项财务事实展示名称、数值、人民币单位、报表期、口径、审计状态和来源按钮；**不要再把「未经审计·合并口径」写死在总标题上**。`null` 显示「未披露」，无可核验证据显示「覆盖资料内暂无已核实记录，不能据此认定无风险」。来源抽屉显示官方链接、公告编号、引用页、短摘录、哈希及资料日期；断网时至少仍可查看本地已缓存的证据信息，外链打不开要如实提示。若补充本地 PDF 打开能力，要确保实际可用、不会和来源清单脱节，不要声称离线时官方站点可访问。
3. 交易情景所有可编辑参数都来自 `/api/demo-scenario` 和用户输入。预付款、账期、延付、成本、现金底线、期初现金、其他现金流、分批发货改变后调用 `/api/simulations` 和 `/api/compare-scenarios`，不在 React 中重写现金算法。前端防抖可以保留，但连续快速更改时不能让旧响应覆盖新结果；正在计算时明确提示、避免旧数字被误认为新结果。金额输入与显示要处理小数、负数、零、空值和单位换算，不能用静态假曲线冒充尚未计算的结果。
4. 时间轴和图表从真实输入/响应生成：成本日、所有发货批次、其他现金流与回款日要与用户改动一致，不能只看第一条现金流或固定标「第 10 天成本」。图表清晰标出 90 天视窗、安全底线、最低点；余款若在第 130/160 天到账，应在视窗外标注，不能让评委误以为坏账或完全没有回款。分批发货时正确呈现对应成本和回款计划；若 API 目前不足以给出逐笔解释，先准确展示已有数据，再提契约变更建议。
5. 方案对比取自 `/api/compare-scenarios`，让用户看得出「维持条款、30% 预付款、分批发货、放弃订单」各自的现金最低点和代价；「放弃订单」需注明放弃预期毛利，不自动说成唯一正确方案。交易建议只能是基于用户设定底线的可考虑动作，不能输出违约概率、信用评级、法律或授信结论。
6. 页面中的**用户角色、决策目标、主标题、主操作文案、输出模板**读 `/api/use-cases`，不复制到企业表或在 JSX 里固定一套。切换已有两种角色应更新文案和核对卡章节，同时使用同一份企业、来源、事件与计算 API。设计可配置的卡片字段渲染规则和未知字段的安全提示；以后仅在 `data/use_cases.json` 追加使用现有字段的新靶向用户时，不需要重写数据模型或核心证据服务。若新场景确实需要新算法，提出独立服务边界，不偷偷塞进证据模型。
7. 完善键盘可操作性、按钮标签、抽屉关闭和焦点、图表文本替代、移动端或窄屏降级。交互要兼顾评委在现场「点错也能回来」：提供明显的重置演示、错误恢复和当前情景状态。不要把真实资料、假设和计算结果混成同一种颜色或标签。

### 4. 明确的数字与验收场景

使用仓库 `data/demo_scenarios.json` 原样验收：订单 1,000,000 元；毛利率 18%，直接成本 820,000 元第 10 天支出；期初现金 3,000,000 元；第 75 天其他业务净流出 2,150,000 元；安全底线 200,000 元；第 10 天发货，账期 90 天，延付压力 30 天，余款第 130 天到账。上述现金与订单数据均为**虚构演示输入**，不是希荻微财报或付款历史。

- 0% 预付款：90 天内最低现金 **30,000 元**（3 万元），第 75 天，底线缺口 **170,000 元**（17 万元）。
- 30% 预付款：最低现金 **330,000 元**（33 万元），未跌破 20 万元底线；预付款和余款之和始终等于订单额。
- 延付 60 天时余款第 160 天到账；账期、发货日、现金流日变化后日期和图表随 API 一致变化。
- 页面中的所有事实均可点到来源，`unknowns` 明示；当前健康信息真实显示 1 家有核验事实的企业和 2 份可访问来源。不得展示「行业覆盖」「风险下降百分比」「预测违约概率」等没有证据的结果。
